Incremental answer profiles — candidate design

Problem: on06717, rebuilding100k responses after cache invalidation still took10.9s cold; active reads included503/timeouts and a45.6s expired transaction. A fixed16MB work_mem budget did not solve it. No production acceptance or resource-plan change.

Decision: keep the existing authorized results transactions, revision cache, API DTOs and privacy suppression. Replace per-request Response/Answer scans with synchronously maintained, backend-only counts of (post,user,canonical answer vector). The vector includes question IDs, option IDs, and text-presence only. Demographics remain in the source tables and are joined at read time, so profile changes and UTC age/day rules remain current.

AnalysisResponseProfile maps each source Response to one AnalysisAnswerProfile. Statement triggers refresh only changed responses; a response lock precedes the source read. Counter changes and source mutations commit or roll back together. Existing AnalysisRevision triggers serialize same-post writes and invalidate in-memory caches. Source user deletion or reassignment fires Response updates; response erasure cascades the map and deletes zero/unreferenced buckets. No independent durable copy of text or demographics is created. Both tables FORCE RLS, provider/default grants are explicitly revoked, functions are SECURITY INVOKER with fixed search_path. Digest collisions fail closed by immutable-identity guard. Raw response IDs and user IDs never enter results DTOs.

Migration is additive and atomic. It takes a five-second bounded attempt to acquire write-conflicting Response/Answer locks, then backfills in5000-response batches inside one transaction with120-second statement timeout. Reads continue; writes wait while migration owns locks. The actual target row count, migration duration, storage headroom and rollback must be checked before production. Failure rolls back all new objects; the existing application tables are not modified. Applying this with an old compatible API is safe because source changes still drive triggers.

Rollback: keep projection tables/triggers and return API to06717 (compatible interaction contracts), accepting its known analytics latency while repairing forward. Do not return API to9fc while new-client mutationId retries remain possible. Old frontend rollback may retain the newer compatible API. A later removal of the projection requires first deploying a source-reading API and verifying no projection readers, then explicitly removing the derived objects; this is not part of the rollout. Source tables remain the rebuild authority. Backup/restore must include triggers/tables or rebuild before enabling the reader.

Acceptance: local synthetic100k backfill, old/new weighted DTO equivalence across all dimensions/filters, full-schema restricted-role HTTP concurrency, provider-role denial, erasure/rollback, hosted varied1k/10k/100k and sustained reads/votes, actual FE rollback and current independent review. Local milliseconds are not hosted performance evidence. No production until F26 and release gates pass.
