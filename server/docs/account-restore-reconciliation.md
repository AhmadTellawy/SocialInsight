# Account restore reconciliation and operator erasure

These offline tools are implementation, not evidence that a hosted recovery has happened. They never restore a provider backup, change a provider fence, start a worker, or reopen the application. Required independent review: E03, E01, E04, D04, E05 and F01. Use the current reviewed application commit, including migration `20260910002000_deletion_decision_journal`, before using the tools. The CLI verifies the Git revision and refuses changed or untracked server source/schema/package files. Run from the committed source checkout; compiled deployment packages without Git metadata are not currently supported.

## Coverage and retention boundary

`deletion_decisions` records ACCOUNT_ERASE and terminal MEDIA_PURGE intent, not provider storage success. It is append only, has no user foreign key and has no automatic TTL. The capture includes every journal row, every current handle alias, all current deleted-account IDs and their exact media pointers, and current PENDING_DELETE/DELETED media pointers. The export does not include email, profile text, credential hashes or post/comment text. IDs, handle aliases and object paths remain sensitive and must stay encrypted.

The continuous-coverage baseline must be an independently verified time after journal coverage became effective for every writer. Only backups at or after that baseline and at or before the final source cutoff are eligible. Existing hard-deleted posts/comments and other unavailable pre-baseline history are **not reconstructed**. An older backup is blocked, even when the retained current deleted-account list looks complete. A capture from before subsequent source writes is insufficient. If the source is lost and no independently retained journal proves complete coverage through the actual final source cutoff, recovery must remain quarantined.

No retention duration or legal approval is invented by these tools. E05 must reconcile journal and encrypted-copy retention with the actual oldest usable backup, outstanding requests and restore obligations. Do not purge journal records or exports automatically. A copy in Storage belonging to the same Supabase project being restored is not an independent recovery source. A path outside Git alone does not prove independence or provider retention.

## Actual fence and source preparation

1. F01/D08 identify the exact application commit, Supabase project, database endpoint/role, backup ID/time, Storage project, all API instances, old deployments, cron/cleanup workers, queue consumers, deployment hooks and administrative writers. Confirm credentials through the already authorized secret store; never put them in command arguments, files in Git, logs or reports.
2. Stop or isolate every identified provider writer. The app maintenance guard is supplemental: it does not stop older builds, already running transactions, external Storage upload capabilities or administrator sessions. Drain in-flight DB transactions, conversions, uploads and cleanup jobs. Preserve evidence of the actual provider actions and observations; do not treat a Boolean environment flag or a signed-looking document as proof.
3. Verify the first-hop certificate/hostname with the reviewed endpoint and strict TLS. Hosted operation additionally requires `pg_stat_ssl.ssl=true` for the database session. With a pooler, this is a different connection leg. A TLS-protected client-to-pooler connection does not establish the pooler-to-database leg. `DATABASE_LEG_TLS_UNVERIFIED` blocks the tool; resolve the verified transport/provider configuration rather than weakening this guard.
4. Keep both the final source and the restored target fenced while capturing and reconciling. Independently review a short-lived receipt bound to the target, revision, fence inventory/stop/drain evidence, coverage baseline and final cutoff. Record the exact receipt file SHA-256 in independent gate evidence. The CLI compares exact bytes to the separately supplied digest. This authenticates byte selection, not the truth of observations or the operator's authority. The same operator computing a hash of an unreviewed file does not satisfy review.
5. Prepare an existing protected directory outside any Git ancestry on an independently retained recovery store. Verify ACLs and recovery access separately, particularly on Windows where Node's `0600` mode is not an ACL guarantee. Supply a dedicated random 32-byte AES key through `RECONCILIATION_ARTIFACT_KEY` as 64 hexadecimal characters. Keep the key in the approved secret store separately from the ciphertext and verify its recovery availability. The tool does not create a new signing-key authority or print the encryption key.

## Environment and receipt contract

Only `RECONCILIATION_DATABASE_URL` is used for these database connections; there is no dotenv load or app startup. Set `RECONCILIATION_ENVIRONMENT` to STAGING or PRODUCTION and `RECONCILIATION_PROJECT_REF` to the verified 20-letter project reference. The URL must exactly match the reviewed receipt endpoint, database and username, use the public schema, and have no target-changing options. Hosted endpoints are restricted to the project-specific Supabase direct endpoint or an exact reviewed AWS session pooler on port 5432. Stage additionally pins `mnfiixtgnlzmduunfryt`. `sslmode=require&sslaccept=strict` is mandatory. Transaction poolers and arbitrary hosts are refused. Connection count is forced to 1 and connection/socket timeouts are bounded.

The LOCAL_SYNTHETIC target only permits `127.0.0.1:55447`, `postgres`, project `local-settings-test`, and databases `settings_test` or `restore_reconciliation_test`. The replay CLI refuses hosted Storage operations for this target; service tests inject a synthetic storage adapter.

All receipts are strict JSON: unknown fields, duplicate CLI flags, invalid time formats and expired windows are rejected. UTC timestamps require canonical milliseconds, e.g. `2026-09-10T01:00:00.000Z`. The window from issuedAt to expiresAt is at most two hours and must remain inside the externally protected fence window. Evidence references are opaque identifiers and SHA-256 digests, not URLs containing access tokens. See the strict Zod schemas in `src/services/restoreReconciliationService.ts` for the executable contract:

- Every receipt: `version:1`, `purpose`, `target:{environment,projectRef,host,port,database,username}`, `sourceRevision` (40-character commit), `issuedAt`, `expiresAt`, `independentReview:{reference,sha256}`, `fence:{id,stoppedAt,drainedAt,protectedThrough,writerInventory,providerStop,databaseDrain,storageWriterDrain}`. Each evidence field is `{reference,sha256}`.
- CAPTURE adds `coverage:{baselineAt,journalEnabledAt,finalSourceCutoff,baselineEvidence,continuousCoverageEvidence}` and `protectedStore:{locationSha256,independentOfProject:true,evidence}`. `finalSourceCutoff` must equal the final source fence's `drainedAt`; `journalEnabledAt <= baselineAt <= finalSourceCutoff`. `locationSha256` is the SHA-256 of the resolved absolute output directory string.
- RESTORE adds `artifactSha256` (full canonical plaintext snapshot digest returned by capture), `sourceCaptureReceiptSha256`, `finalSourceCutoff`, `finalCoverageEvidence`, `backup:{id,capturedAt,projectRef,evidence}`, and `independentSource:{locationSha256,independentOfProject:true,evidence}`. The project, commit, final cutoff and capture receipt digest must exactly match the authenticated snapshot. The backup must lie within coverage. Independent source location binds the actual input artifact directory.
- ACCOUNT_ERASE adds stable `decisionId`, one `subjectId`, and `privacyRequest:{id,scope:'ACCOUNT_ERASE',verifiedAt,verificationEvidence,authorityEvidence}`. The receipt binds the verified request scope, account and stable decision ID. It is not a bulk SQL or arbitrary-content deletion interface. Request identifiers and subject IDs belong in protected storage, not task logs.

## Commands

Use an existing reviewed Node/Prisma installation. These examples use placeholders, not executable evidence or credentials. Set environment secrets using the approved provider/secret-store path before invoking. Run from `server/` in the clean reviewed checkout:

```text
node -r ts-node/register src/scripts/captureRestoreReconciliation.ts --receipt=ABSOLUTE_PROTECTED_RECEIPT --receipt-sha256=INDEPENDENT_REVIEW_DIGEST --output=ABSOLUTE_PROTECTED_NEW_CIPHERTEXT
node -r ts-node/register src/scripts/replayRestoreReconciliation.ts --receipt=ABSOLUTE_PROTECTED_RESTORE_RECEIPT --receipt-sha256=INDEPENDENT_REVIEW_DIGEST --artifact=ABSOLUTE_PROTECTED_CIPHERTEXT --checkpoints=ABSOLUTE_PROTECTED_EXISTING_DIRECTORY
node -r ts-node/register src/scripts/executePrivacyErasure.ts --receipt=ABSOLUTE_PROTECTED_REQUEST_RECEIPT --receipt-sha256=INDEPENDENT_REVIEW_DIGEST --checkpoints=ABSOLUTE_PROTECTED_EXISTING_DIRECTORY
```

Capture is read only against PostgreSQL. Its single repeatable-read, read-only transaction captures a complete stable snapshot under the external fence. It rejects undrained non-idle sessions, unexpected SQL database/role identity, invalid journal contents and record/byte limits; it does not truncate. Maximum per collected table/list is 100,000 rows and maximum canonical plaintext artifact is 64 MiB. Exceeding the bound requires a separately reviewed streaming solution, not partial export. Output is AES-256-GCM with a random nonce, authenticated digest and exclusive create + file fsync. No plaintext artifact is written. Power-loss durability, offsite replication and successful recoverability of the output/key require independent operational verification; file fsync alone does not prove them.

Replay and erasure default to dry-run. After independent review of the concrete plan and receipt, add the explicit `--apply` switch under the existing task authority. Replay additionally requires `SUPABASE_URL` to exactly equal the receipt project URL and `SUPABASE_SERVICE_ROLE_KEY` from its approved secret store. No credentials are displayed. Ordinary failures emit only a fixed code. Preserve the encrypted checkpoints and the receipt/digest on every failure. A process interruption means unknown outcome; retain the fence and inspect the journal/checkpoints before idempotently retrying with a fresh reviewed receipt if the previous window expired.

## Reconciliation and release semantics

The encrypted PLANNED checkpoint is persisted before the first mutation. Each account is processed through the same trusted transactional purge as live account erasure, without simulating an HTTP session. Restored credentials, sessions and profile identifiers are purged again even when the immutable decision already exists. Aliases are merged without taking another owner's name. Aliases belonging to a post-backup account absent from the restored DB become reserved tombstones. Any ownership or current-handle conflict stops reconciliation for review.

Terminal media decisions are replayed against exact normalized bucket/key pointers, including objects absent from the restored DB. Current restored pointers are included and owner checked. The maximum captured/restored `deleteNotBefore` is honored before any offline storage deletion. Pending grace periods block completion. Live cleanup may revoke currently present bytes earlier while retaining the pointer and pending state for a second removal after upload capabilities expire; this offline tool uses the more conservative no-early-I/O rule. Storage failure cannot become successful completion. A rerun reuses the immutable decision and deletes the same exact keys. No bucket listing or recursive/prefix delete is performed.

No group is automatically assigned a new owner. Every replay queries all non-deleted groups without an active joined Owner, including groups whose membership was removed during an interrupted earlier attempt. Their IDs are retained in encrypted checkpoints. Such groups keep the result BLOCKED until the separate reviewed ownership resolution is applied. An account erasure result `ERASED_STORAGE_CLEANUP_PENDING` is logical erasure, not a claim that object cleanup completed.

`RECONCILED_FENCE_REMAINS` means only these reconciliation checks completed. It never authorizes or performs reopening. Before F01 can reopen: verify absence of resurrected auth/profile data, reserved handles, deleted media objects and late uploads; resolve ownerless groups; finish pending media grace and storage retries; validate migrations/ACL/RLS, OAuth/OTP and app smoke; verify operator request history and backup/storage recovery evidence; obtain independent E03/E01/E04/E05/D04/F01 disposition for the exact revision and target. Observe logs/health after the separately authorized reopen.

## Local evidence and limits

Focused tests cover receipt tampering, target/TLS mismatches, encryption authentication, forbidden file locations/overwrites, coverage/count conflicts, alias ownership, zero-mutation dry-run, orphan object replay, retry after storage failure, grace deadlines, ownerless-group recurrence and narrow request scope. Dedicated PostgreSQL rehearsal applies all 18 migrations to a synthetic database and verifies actual journal capture, credential/session erasure after recreating old row state, alias preservation and idempotent replay. The storage adapter is synthetic, and recreated row state is not a pg_dump/PITR/provider restore. No hosted mutation, actual independent recovery store, production backup, offsite key recovery or real-user erasure is proven by these tests.

### Deadline and actual backup rehearsal follow-up

The expiry correction additionally bounds Prisma acquisition/execution by the remaining receipt window, sets PostgreSQL 17 `transaction_timeout` locally for each guarded transaction, checks every awaited Prisma operation before/after execution, and propagates a per-operation abort signal to Supabase fetch. A delayed or unresponsive storage call cannot finalize the media row or record a successful return after expiry. Aborting an HTTP request does not prove the remote operation never occurred; retain the fence and reconcile the exact keys on an unknown outcome.

A subsequent bounded local rehearsal used the official PostgreSQL-linked EDB 17.11 client ZIP to perform a real custom-format pg_dump and pg_restore of only the dedicated synthetic database. Its official HTTPS provenance, exact reproducibility hashes, unavailable publisher checksum and unsigned Authenticode status were recorded and accepted for that synthetic-only toolkit use; no signed-artifact claim was made. The backup genuinely restored active credentials/session data and removed decisions/aliases created after backup. The independently retained encrypted local fixture then drove re-erasure, tombstone reconstruction and idempotent replay, preserving all 18 migration checksums. This proves local binary backup/restore mechanics; provider restore/PITR, cloud Storage, offsite durability and independent key recovery remain unverified.
